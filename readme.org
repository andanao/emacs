#+TITLE: Emacs Configuration
#+STARTUP: overview

Plain elisp, split by domain.  A flake pins the packages; nothing else.

This used to be one literate org file that tangled into a 6000-line
~init.el~.  It is now ~37~ files that are the source, edited directly.  Nix
supplies the package set and owns nothing else, so every file here stays
live-editable.

* Running it
Build the package set and start Emacs against this directory:

#+begin_src shell
nix build
result/bin/emacs --init-directory ~/git/emacs-nix
#+end_src

~nix build .#packageNames~ writes the resolved package list without building
Emacs, which is the quick way to see what the parser made of a new
~use-package~ form.

Cutover is repointing ~~/.emacs.d/init.el~ and ~early-init.el~ at this repo.
Rollback is pointing them back.

* Layout
~init.el~ loads every file below in a fixed order, the same order the old
literate config tangled into.  Files resolve against wherever ~init.el~ really
lives, following the symlink, so they are found whether Emacs is started with
~--init-directory~ or through ~~/.emacs.d~.

** Root
~early-init.el~ runs before the frame exists.  ~mac.el~, ~linux.el~ and
~ms-windows.el~ are loaded by ~config/platform.el~ on the matching system.

* What Nix owns
Packages, and only packages.  ~flake.nix~ reads every ~use-package~ form under
~config/~ and ~lisp/~ and builds an Emacs carrying exactly those.  There is no
elisp in the flake and nothing of this config goes into the store.

~package.el~ still runs, since it is what loads the packages' autoloads, but
~package-user-dir~ points away from ~~/.emacs.d/elpa~ so the old tree cannot
get in front of the pinned set.

Six packages are installed from git rather than MELPA and are pinned by
revision in ~gitSources~.  Bumping one is a rev and a hash.

Every tree-sitter grammar nixpkgs ships comes from the store too, so no mode
stops to ask for one.

* Installing and upgrading packages
- *Install.*  Add a ~use-package~ form in the right ~config/~ file, then check
  ~nix build .#packageNames~ and the source it resolved.  Not ~M-x
  package-install~: ~package-user-dir~ is pointed away from ~~/.emacs.d/elpa~.
- *Upgrade.*  ~nix flake update~, or ~nix flake update emacs-overlay~ for the
  overlay alone, then rebuild and restart.  ~flake.lock~ is the pin, so commit
  it.  ~M-x package-upgrade~ does nothing here.
- *Upgrade, git packages.*  A new rev, hash and version in ~gitSources~.
- *Rollback.*  ~git checkout flake.lock~ and rebuild.

* Known leaks
Things Nix does not pin here, each for a reason:

- *Language servers.*  ~lsp-mode~ downloads rust-analyzer and pyright on first
  use.  Out of scope: they are system tools and belong to the machine config,
  not the editor's package set.
- *ghostel's native module.*  The flake takes the elisp from ~lisp/~ and not
  the Zig terminal around it, so ~ghostel-module.dylib~ is still whatever
  ~ghostel-module-install~ put there.  ~package-vc~ never supplied it either, so
  this is unchanged rather than lost.
- *toggl.*  A private repo reached over SSH, which no pure evaluation can
  fetch.  Making it public, or vendoring it, is what would close this.
- *Emacs state.*  ~custom.el~, ~eln-cache~, history, bookmarks and
  ~.org-id-locations~ resolve against ~user-emacs-directory~ and are ignored by
  git.  They are per-machine by nature.
